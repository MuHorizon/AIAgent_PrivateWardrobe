# AI 私人衣橱 Agent 小程序项目文档

## 1. 项目定位

AI 私人衣橱 Agent 是一个面向微信小程序的个人穿搭助手。用户上传自己的衣服后，系统通过视觉模型理解衣物信息，结合用户画像、穿衣偏好、天气、场景和历史反馈，主动生成穿搭方案，并在后续版本中提供 AI 虚拟试穿和购物搭配建议。

这个项目不只是一个“AI 推荐衣服”的小工具，而是一个完整的 AI Agent 练习项目，核心能力包括：

- 视觉理解：识别衣物类别、颜色、风格、季节、适合场景。
- 长期记忆：记录用户身材信息、风格偏好、颜色偏好、历史反馈。
- 工具调用：调用天气 API、图片识别、图片生成、商品分析等外部能力。
- 任务规划：把用户自然语言需求拆解为查询、筛选、搭配、解释、保存等步骤。
- 生成能力：生成穿搭文案、搭配理由，后续生成试穿效果图。

## 2. 目标用户

适合以下用户：

- 衣服不少，但每天不知道怎么搭配。
- 想根据天气、场景、约会、通勤、旅行等需求快速决定穿什么。
- 买衣服前想知道新衣服能不能和已有衣柜搭配。
- 希望 AI 逐渐了解自己的风格，而不是每次都重新描述偏好。

## 3. 核心使用流程

第一版建议先聚焦一个完整闭环：

1. 用户微信登录。
2. 用户填写基础穿衣画像。
3. 用户上传衣服照片。
4. AI 自动识别衣物属性。
5. 系统建立个人衣柜。
6. 用户输入场景需求。
7. AI Agent 查询衣柜并生成穿搭方案。
8. 用户收藏、评价或保存穿搭记录。
9. 系统把反馈沉淀为用户长期记忆。

### 3.1 每一步对应的 Agent 知识点

这个项目的学习重点不是单纯把页面做出来，而是理解“业务动作背后对应 Agent 的什么能力”。下面把第一版流程拆成学习视角。

| 业务步骤 | Agent 知识点 | 技术点 | 说明 |
| --- | --- | --- | --- |
| 微信登录 | 用户身份上下文 | 微信登录、openid、session、uni-id | Agent 必须知道“当前用户是谁”，否则无法读取该用户的衣柜和记忆。 |
| 填写用户画像 | Memory 初始化 | 表单、数据库、用户画像表 | 这是长期记忆的第一批数据，例如身高、体重、风格偏好、颜色偏好。 |
| 上传衣服 | 多模态输入 | 图片上传、云存储、图片压缩 | 用户给 Agent 的输入不只是文字，也可以是图片。 |
| AI 识别衣服 | Vision 模型 | 图像理解、结构化输出 JSON | 让 AI 把图片变成可查询的数据，例如颜色、类别、季节、场景。 |
| 确认识别结果 | 人类反馈 | 表单编辑、数据修正 | AI 可能识别错，用户修正后能提高数据质量。 |
| 建立衣柜 | 工具数据源 | 云数据库、分类查询 | 衣柜就是 Agent 后续推荐时要查询的私有数据库。 |
| 输入场景 | Context 构建 | Prompt、意图识别、上下文拼接 | 用户说“明天海边 30 度怎么穿”，Agent 要提取场景、天气、目标。 |
| 查询衣柜 | Tool Calling / RAG | 数据库查询、标签筛选、向量检索 | Agent 不能凭空推荐，必须调用工具查询用户真实拥有的衣服。 |
| 生成穿搭 | LLM 推理规划 | 规则约束、方案排序、结构化输出 | LLM 负责组合衣服、解释理由、给出搭配方案。 |
| 保存反馈 | 长期记忆更新 | feedback 表、ai_memory 表 | 用户喜欢或不喜欢，会变成下一次推荐的记忆。 |
| 历史记录 | 会话与任务管理 | outfit_records、ai_tasks | 方便复盘 Agent 做过什么，也方便排查错误。 |

### 3.2 本项目中的 Agent 结构

可以把本项目理解成下面这个结构：

```text
用户
  -> 微信小程序
  -> AI 私人衣橱 Agent
      -> Context：当前问题、用户画像、天气、衣柜数据
      -> Memory：长期偏好、历史穿搭、用户反馈
      -> Skills：穿搭规则、颜色搭配规则、场景规则
      -> Tools：查衣柜、查天气、识别图片、保存记录
      -> LLM：理解需求、规划步骤、生成答案
```

其中：

- `Context` 是本次对话临时要用的信息。
- `Memory` 是跨会话长期保存的信息。
- `Skills` 是提前写好的能力说明和业务规则。
- `Tools` 是 Agent 可以真正调用的功能。
- `LLM` 是负责理解、推理和生成结果的大模型。

场景偏好：

### 4.3 上传衣服

用户可以通过拍照或相册上传衣服图片。

- 上衣
- 下装
- 外套
- 鞋
- 包
- 配饰

上传后进入 AI 识别流程。

### 4.4 AI 衣物识别

用户上传一张衣服图片后，AI 识别并结构化保存：

```json
{
  "category": "上衣",
  "type": "短袖T恤",
  "color": "白色",
  "material": "棉",
  "fit": "宽松",
  "style": ["休闲", "简约"],
  "season": ["春", "夏"],
  "scene": ["日常", "旅行", "海边"],
  "description": "一件白色宽松短袖T恤，适合夏季休闲场景。"
}
```

用户可以确认或手动修正 AI 识别结果，避免错误数据进入衣柜。

### 4.5 我的衣柜

系统根据 AI 识别结果自动分类展示衣物。

衣柜页面建议分为：

- 全部
- 上衣
- 下装
- 外套
- 鞋
- 包
- 配饰

每件衣服展示：

- 图片
- 名称
- 颜色
- 风格标签
- 季节标签
- 常用场景

### 4.6 AI 穿搭 Agent

用户可以输入自然语言需求，例如：

> 明天去海边玩，30 度，怎么穿？

Agent 执行流程：

1. 理解用户意图：识别场景、温度、风格、舒适度需求。
2. 查询用户画像：读取身材、风格、颜色偏好。
3. 查询衣柜：筛选适合季节、场景、颜色和风格的衣物。
4. 规划搭配：组合上衣、下装、鞋、配饰。
5. 生成说明：解释为什么这样搭配。
6. 保存结果：用户确认后写入穿搭历史。

输出示例：

```json
{
  "scene": "海边",
  "weather": "晴天，30度",
  "outfits": [
    {
      "title": "清爽海边休闲搭配",
      "items": ["白色宽松T恤", "卡其短裤", "凉鞋", "棒球帽"],
      "reason": "白色和卡其色适合夏季海边，整体轻便透气，帽子可以增强防晒。",
      "score": 92
    },
    {
      "title": "防晒轻度度假搭配",
      "items": ["浅蓝色宽松衬衫", "黑色短裤", "运动鞋"],
      "reason": "衬衫可以防晒，黑色短裤更耐脏，适合海边散步和拍照。",
      "score": 86
    }
  ]
}
```

### 4.7 穿搭历史与反馈

用户可以对 AI 推荐结果进行操作：

- 收藏
- 不喜欢
- 今天穿这套
- 太热
- 太正式
- 不喜欢颜色
- 换一套

这些反馈会进入 AI Memory，影响后续推荐。

### 4.8 当前实现进度

已完成第一版端到端闭环：

- 豆包文本模型配置：API Key、文本模型、接口地址都从云函数环境变量读取。
- 豆包视觉识别：上传衣物图片后可调用 `client/wardrobe/clothes.analyze` 自动填充衣物字段。
- 衣柜检索工具：生成穿搭前会按场景、温度、画像和历史反馈筛选最多 40 件候选衣物。
- 偏好 Memory：收藏、不喜欢、今天穿会被压缩成颜色、分类、风格偏好摘要，进入下一次推荐上下文。
- 输出校验与重试：豆包输出必须是 JSON，且 `clothes_ids` 必须来自真实衣柜；失败会重试一次，再失败进入规则兜底。
- 穿搭解释：结果包含推荐理由、重点单品、天气建议和替换建议。
- AI 任务日志：`ai_tasks` 记录 Prompt 摘要、原始输出、重试错误、兜底原因和任务状态。
- 调试入口：小程序首页进入“AI 调试”，可查看配置状态和最近任务。

还需要部署后人工完成：

- 在 uniCloud 云函数环境变量配置真实 `ARK_API_KEY`。
- 如果文本和视觉使用不同接入点，分别配置 `ARK_TEXT_MODEL` 和 `ARK_VISION_MODEL`。
- 上传数据库 schema 和 router 云函数后，用真机测试图片识别和生成穿搭。

## 5. 第二版功能

### 5.1 天气工具调用

引入天气 API 后，Agent 不再只依赖用户输入的温度，而是根据用户所在城市自动查询天气。

天气字段建议包括：

- 城市
- 温度
- 天气状态
- 降雨概率
- 风力
- 紫外线
- 体感温度

推荐逻辑示例：

- 下雨：优先推荐防水鞋、外套、深色裤子。
- 降温：提醒增加外套。
- 紫外线强：推荐帽子、长袖衬衫、防晒外套。
- 高温：推荐浅色、宽松、透气材质。

### 5.2 AI 虚拟试穿

用户上传本人正面照，并选择衣服组合后，系统调用 AI 图像生成或虚拟试穿模型生成试穿效果。

试穿输入：

- 用户照片
- 上衣图片
- 下装图片
- 鞋或配饰图片
- 穿搭风格说明

试穿输出：

- 单品试穿图
- 完整 Look 试穿图
- 可保存到穿搭历史

注意：虚拟试穿对图片质量、姿势、背景、模型能力要求较高，不建议放在第一版。

## 6. 第三版功能

### 6.1 购物搭配 Agent

用户上传网上看到的衣服图片，AI 分析该商品能否和已有衣柜搭配。

输出内容：

- 商品风格
- 商品颜色
- 适合场景
- 与现有衣柜的匹配度
- 可搭配的已有衣物
- 预计可形成多少套穿搭
- 是否值得购买

示例：

```json
{
  "item": "黑色短款夹克",
  "style": ["街头", "休闲"],
  "match_score": 92,
  "matched_clothes": ["白色T恤", "蓝色牛仔裤", "黑色马丁靴"],
  "estimated_outfits": 8,
  "suggestion": "值得购买。你的衣柜中已有多件基础款可以搭配这件夹克。"
}
```

## 7. Agent 架构设计

### 7.1 Agent 输入

输入来源包括：

- 用户自然语言问题
- 用户画像
- 衣柜数据
- 天气数据
- 历史穿搭
- 用户反馈
- 上传的衣服或商品图片

### 7.2 Agent 工具

建议抽象以下工具：

- `get_user_profile`：查询用户画像。
- `search_closet`：查询用户衣柜。
- `get_weather`：查询天气。
- `analyze_clothing_image`：识别衣服图片。
- `generate_outfit`：生成穿搭方案。
- `save_outfit_record`：保存穿搭历史。
- `update_user_memory`：更新用户长期记忆。
- `virtual_try_on`：生成虚拟试穿图，第二版接入。
- `analyze_shopping_item`：分析购物图片，第三版接入。

### 7.3 Agent 工作流

推荐工作流：

```text
用户请求
  -> 意图识别
  -> 补全上下文
  -> 调用工具查询数据
  -> 生成候选穿搭
  -> 根据用户偏好排序
  -> 输出方案与理由
  -> 等待用户反馈
  -> 更新 Memory
```

## 10. 技术方案建议

当前项目是 `uni-app` 结构，可以继续使用微信小程序方向。

建议技术栈：

- 前端：uni-app / Vue
- 小程序平台：微信小程序
- 后端：uniCloud 云函数
- 数据库：uniCloud 云数据库
- 图片存储：uniCloud 云存储或对象存储
- AI 接口：LLM + Vision + Image Generation
- 天气接口：第三方天气 API

第一版先不要过度设计复杂 Agent 框架，可以先实现稳定的业务工具函数，再把它们编排成 Agent 工作流。

### 10.1 本项目会用到的 AI Agent 技术

下面这部分是学习重点。后续写代码时，每个功能都应该对应到这里的某个 Agent 知识点。

| Agent 技术 | 在本项目中的用途 | 第一版是否需要 |
| --- | --- | --- |
| `System / User / Assistant` 角色 | 设置 AI 的身份、接收用户问题、返回搭配建议 | 需要 |
| Context 上下文 | 把用户问题、画像、衣柜、天气、规则一起发给模型 | 需要 |
| Prompt Engineering | 约束 AI 按固定 JSON 输出，避免乱答 | 需要 |
| Function Tool | 让 AI 调用查衣柜、保存记录、查天气等函数 | 需要 |
| Memory 长期记忆 | 记住用户喜欢黑白灰、宽松、不喜欢花衬衫 | 需要 |
| Vision 多模态识别 | 识别用户上传的衣服图片 | 需要 |
| 结构化输出 | 让 AI 返回稳定字段，方便前端展示和数据库保存 | 需要 |
| 会话管理 | 保存用户每次搭配对话和历史结果 | 需要 |
| Token 优化 | 控制上下文长度，避免每次发送全部衣柜和全部历史 | 需要 |
| RAG / 检索 | 从大量衣服或记忆中找最相关的数据 | 第二阶段重点 |
| Embedding 向量化 | 把衣服描述和用户偏好转成向量，支持相似搜索 | 第二阶段重点 |
| SSE 流式输出 | 让 AI 搭配建议逐字展示，提升聊天体验 | 第二阶段可做 |
| MCP 协议 | 把天气、商品、图片服务包装成标准工具 | 学习阶段可了解 |
| Image Generation | 生成 AI 试穿效果图 | 第二版需要 |
| Workflow 编排 | 把理解需求、查衣柜、搭配、保存反馈串起来 | 需要 |

### 10.2 AI 角色设计

大模型接口里常见三种角色：

- `system`：系统提示词，告诉 AI 它是谁、能做什么、不能做什么、输出格式是什么。
- `user`：用户输入，例如“明天去海边玩，30 度，怎么穿？”
- `assistant`：AI 返回的内容，例如穿搭方案和理由。

本项目的 `system` 可以写成一个固定提示词文件，后端每次调用 AI 时都带上。

示例：

```text
你是一个 AI 私人衣橱 Agent。
你只能根据用户真实衣柜中的衣服进行推荐，不能编造用户没有的衣服。
你需要结合用户画像、天气、场景、颜色偏好和历史反馈生成搭配。
请输出 JSON，字段包括 scene、weather、outfits、reason、score。
如果衣柜中没有合适衣服，请明确说明缺少什么类型的衣服。
```

学习重点：

- `system` 决定 AI 的工作边界。
- `user` 提供当前需求。
- `assistant` 返回符合业务要求的结果。
- 好的 Agent 不是只靠用户一句话，而是后端帮它拼好上下文和工具结果。

### 10.3 Context 上下文设计

大模型本身不知道你的业务，也不知道用户衣柜里有什么，所以必须提供上下文。

本项目一次推荐穿搭时，建议传给 AI 的上下文包括：

```json
{
  "user_request": "明天去海边玩，30度，怎么穿？",
  "user_profile": {
    "gender": "男",
    "height": 178,
    "weight": 70,
    "body_type": "偏瘦",
    "preferred_styles": ["简约", "休闲"],
    "liked_colors": ["黑色", "白色", "灰色"],
    "disliked_colors": ["黄色", "荧光色"]
  },
  "closet_items": [
    {
      "name": "白色宽松T恤",
      "category": "上衣",
      "color": "白色",
      "scene_tags": ["日常", "旅行", "海边"]
    }
  ],
  "memory": [
    "用户更喜欢宽松版型。",
    "用户最近多次拒绝花色衬衫。"
  ],
  "rules": [
    "高温优先推荐透气材质。",
    "海边场景需要考虑防晒。"
  ]
}
```

学习重点：

- Context 不是越多越好，而是要放“本次任务必要的信息”。
- 第一版可以直接查数据库后拼上下文。
- 后续衣服和历史变多后，要用 RAG 或筛选逻辑，只取最相关的衣服和记忆。

### 10.4 Prompt 与 Markdown 展示

AI 返回结果可以有两种方式：

1. 返回 JSON，前端用卡片展示。
2. 返回 Markdown，前端用 Markdown 组件展示。

小程序里更建议第一版用 JSON，因为穿搭方案要展示成固定 UI 卡片。

如果后面做聊天式回答，可以使用 Markdown 展示：

- Vue / uni-app：可以考虑 Markdown 渲染组件。
- H5 端常见方案：`@crazydos/vue-markdown`、`remark-gfm`。
- React 端常见方案：`react-markdown`、`remark-gfm`。

学习重点：

- JSON 适合业务数据。
- Markdown 适合长文本回答。
- Agent 项目里经常要求 AI “按固定格式输出”，否则前端很难稳定展示。

### 10.5 Function Tool 工具调用

Agent 真正“干活”的关键是工具。模型自己不能查数据库、不能上传图片、不能保存记录，所以需要后端提供工具函数。

本项目第一版建议先做这些工具函数：

```text
getUserProfile(userId)
  查询用户画像

searchCloset(userId, filters)
  按分类、季节、场景、颜色查询衣柜

clothes.analyze 内直接调用 OpenAI SDK
  用 input_image/input_text 识别衣服属性

generateOutfit(context)
  调用 LLM 生成穿搭方案

saveOutfitRecord(userId, outfit)
  保存穿搭历史

updateUserMemory(userId, feedback)
  根据用户反馈更新长期记忆
```

学习重点：

- Tool 是 AI 和真实业务系统之间的桥。
- 第一版可以由代码按固定顺序调用工具。
- 后续可以让 LLM 自己决定下一步调用哪个工具，这才更接近完整 Agent。

### 10.6 Memory 长期记忆

本项目的 Memory 分两类。

短期记忆：

- 当前这一次聊天的上下文。
- 用户刚刚说的话。
- 本次已经生成过的搭配。

长期记忆：

- 用户身高、体重、体型。
- 用户喜欢的颜色和风格。
- 用户不喜欢的衣服类型。
- 用户历史穿搭记录。
- 用户对推荐结果的反馈。

长期记忆示例：

```json
{
  "memory_type": "style_preference",
  "content": "用户更喜欢黑白灰配色、宽松版型、简约休闲风。",
  "source": "user_feedback",
  "weight": 0.9
}
```

学习重点：

- Memory 不是简单保存聊天记录，而是提炼“对以后有用的信息”。
- 用户反馈越多，Agent 越像私人助理。
- 第一版可以手动规则更新记忆，例如用户点“不喜欢颜色”就写入 disliked_colors。
- 后续可以让 LLM 总结用户长期偏好。

### 10.7 RAG 与 Embedding

RAG 的意思是“检索增强生成”。当用户衣柜和历史记录越来越多时，不能把全部数据都塞给 AI，需要先检索相关内容。

在本项目中，RAG 可以用于：

- 从几百件衣服里找适合“海边、夏天、休闲”的衣服。
- 从历史反馈中找和当前场景相关的偏好。
- 从穿搭知识库中找颜色搭配、场景搭配规则。

基础流程：

```text
衣服描述 / 用户记忆 / 穿搭知识
  -> 文本切割
  -> Embedding 向量化
  -> 存入向量数据库
  -> 用户提出需求
  -> 将需求向量化
  -> 检索相似内容
  -> 把检索结果放入 Context
  -> LLM 生成答案
```

学习重点：

- Embedding 是把文字变成数字向量。
- 向量数据库负责找“语义相似”的内容。
- 同一批数据最好不要中途更换 Embedding 模型，否则新旧向量不一致。
- 第一版可以先不用向量数据库，用普通数据库标签筛选。
- 第二阶段再加 RAG，更容易理解差异。

### 10.8 Token、缓存与上下文优化

调用大模型会消耗 token。上下文越长，成本越高，速度越慢。

本项目要注意：

- 不要每次把用户全部衣服都发给 AI。
- 不要每次把所有历史聊天都发给 AI。
- 只传本次推荐需要的衣服、用户画像、关键记忆。
- 对很长的历史记录做总结，再把总结作为 Memory 使用。

示例策略：

```text
最近 10 轮聊天：保留原文。
更早的聊天：让 AI 总结成用户偏好。
衣柜数据：先按场景、季节、分类筛选，再发给 AI。
输出内容：限制返回 2-3 套方案，不要无限生成。
```

缓存可以理解为“之前处理过的输入可以复用结果”。如果系统提示词和固定规则长期不变，部分模型服务可能会对重复输入做缓存优化。

学习重点：

- 命中缓存：类似之前读过的内容可以复用。
- 未命中缓存：新内容需要重新处理。
- 真正开发时，更重要的是减少无关上下文。

### 10.9 会话管理

会话管理解决几个问题：

- 用户刷新页面后，对话不能丢。
- 不同用户只能看到自己的历史。
- 用户可以新建一次新的穿搭咨询。
- 后端可以追踪每次 AI 调用输入和输出。

建议增加会话相关数据：

```json
{
  "conversation_id": "会话ID",
  "user_id": "用户ID",
  "title": "海边穿搭咨询",
  "messages": [
    {
      "role": "user",
      "content": "明天去海边玩怎么穿？"
    },
    {
      "role": "assistant",
      "content": "推荐白色T恤搭配卡其短裤。"
    }
  ],
  "created_at": "创建时间",
  "updated_at": "更新时间"
}
```

学习重点：

- 对话记录是短期上下文的来源。
- 穿搭历史是业务记录。
- AI 任务记录是调试和排错用的日志。

### 10.10 SSE 流式输出

SSE 可以让 AI 像聊天一样逐字输出，而不是等全部生成完再一次性显示。

本项目中可以用在：

- AI 聊天入口。
- 正在生成搭配方案。
- 正在解释搭配理由。

第一版可以先不用 SSE，直接等待 AI 返回完整 JSON。等核心功能稳定后，再加入流式输出。

学习重点：

- SSE 解决的是体验问题，不是 Agent 能力本身。
- 结构化 JSON 输出不太适合逐字流式展示。
- 聊天式 Markdown 回答更适合 SSE。

### 10.11 MCP 协议

MCP 可以理解为 Function Tool 的标准化协议。以前每个工具都用自己的接口格式，MCP 希望让工具接入更统一。

MCP 可以提供：

- `Tool`：让 AI 调用功能，例如查天气、查商品、操作浏览器。
- `Resource`：提供资源，例如读取文件、读取数据库内容。
- `Prompt Template`：提供固定提示词模板。

本项目中可以先不用 MCP，先用普通云函数实现工具。等理解 Tool Calling 后，再学习如何把工具封装成 MCP 服务。

学习重点：

- Tool 是能力。
- MCP 是工具能力的标准协议。
- 对小白来说，先理解“AI 调用函数”，再理解 MCP 会更顺。

### 10.12 多模态能力

本项目非常适合学习多模态，因为输入和输出都不只是文字。

多模态输入：

- 用户上传衣服图片。
- 用户上传本人照片。
- 用户上传网上商品图。

多模态输出：

- 衣物识别结果。
- 搭配方案卡片。
- AI 试穿效果图。

学习重点：

- Vision 模型负责“看图并理解”。
- LLM 负责“结合上下文做决策”。
- Image Generation 负责“生成试穿效果图”。
- 一个完整 Agent 可以同时使用文字、图片、数据库和工具。

### 10.13 Skills 如何融入

Skills 可以理解为 Agent 预先掌握的专业规则。在本项目中，Skills 不是用户数据，而是通用穿搭知识。

可以沉淀的 Skills：

- 颜色搭配规则。
- 不同场景穿搭规则。
- 不同天气穿搭规则。
- 不同体型穿搭建议。
- 男装 / 女装基础分类规则。

示例：

```text
海边场景：
- 优先选择浅色、透气、休闲、方便活动的衣物。
- 高温时避免厚重材质。
- 紫外线强时推荐帽子、薄外套或长袖衬衫。
```

学习重点：

- Memory 是“某个用户的私人偏好”。
- Skills 是“所有用户都适用的专业知识”。
- Context 是“本次任务临时组装的信息”。

## 13. 后续代码注释规范

因为这个项目的主要目的之一是学习 AI Agent，所以后续写代码时要比普通业务项目多写一些“学习型注释”。注释不只是解释代码语法，而是解释这段代码对应 Agent 的哪个概念。

### 13.1 注释原则

后续代码中建议保留三类注释：

- 业务注释：解释这段代码在产品流程里做什么。
- Agent 注释：解释这段代码对应 Context、Memory、Tool、RAG、Vision 还是 Workflow。
- 风险注释：解释为什么要校验、为什么要限制输出、为什么不能信任 AI 原始结果。

不建议写无意义注释，例如：

```js
// 定义变量
const userId = params.user_id;
```

建议写成：

```js
// Agent 必须基于当前用户的私有衣柜工作，所以所有查询都要带 userId，避免串用其他用户的数据。
const userId = params.user_id;
```

### 13.2 云函数注释示例

```js
/**
 * 生成穿搭方案
 *
 * Agent 学习点：
 * 1. Context：把用户问题、用户画像、衣柜数据组装成模型可理解的上下文。
 * 2. Tool：先查询数据库中的真实衣服，再让 AI 推荐，避免 AI 编造不存在的衣服。
 * 3. Structured Output：要求模型返回固定 JSON，方便前端展示成穿搭卡片。
 */
async function generateOutfit(userId, userMessage) {
  // Memory：读取用户长期偏好，例如喜欢黑白灰、不喜欢紧身裤。
  const profile = await getUserProfile(userId);

  // Tool：查询用户真实衣柜。AI 只能基于这些衣服做推荐。
  const closetItems = await searchCloset(userId, {
    scene: "daily"
  });

  // Context：把本次任务需要的信息拼成提示词，不要把无关历史全部塞进去。
  const context = buildOutfitContext({
    userMessage,
    profile,
    closetItems
  });

  return callLLM(context);
}
```

### 13.3 AI 调用注释示例

```js
/**
 * 调用视觉模型识别衣服
 *
 * Agent 学习点：
 * 1. Multimodal：输入是一张图片，不是普通文本。
 * 2. Vision：模型负责把图片理解成衣物属性。
 * 3. JSON Output：返回结构化字段后，衣服才能被数据库检索。
 */
async function clothesAnalyzeVisionSnippet(imageUrl) {
  // 这里要求 AI 只返回 JSON，避免返回一大段自然语言导致后端无法解析。
  const prompt = `
请识别图片中的衣服，并返回 JSON。
字段包括 category、type、color、material、fit、style、season、scene、description。
`;

  return callVisionModel({
    imageUrl,
    prompt
  });
}
```

### 13.4 前端注释示例

```js
/**
 * 用户点击“生成搭配”
 *
 * Agent 学习点：
 * 前端不直接拼 AI 提示词，只负责收集用户输入。
 * 真正的 Context 组装、Tool 调用、Memory 查询都应该放在后端，避免泄露规则和密钥。
 */
async function handleGenerateOutfit() {
  if (!sceneText.value) {
    uni.showToast({
      title: "请先输入穿搭场景",
      icon: "none"
    });
    return;
  }

  await callGenerateOutfitCloudFunction({
    sceneText: sceneText.value
  });
}
```

### 13.5 文档与代码同步要求

后续每完成一个功能，建议同步更新本文档：

- 新增了哪个页面。
- 新增了哪个云函数。
- 这个功能用到了哪个 Agent 知识点。
- 当前功能还有什么限制。
- 下一步准备优化什么。

这样这个项目不仅是成品，也是完整学习记录。

## 14. 项目学习价值

这个项目能覆盖 AI Agent 开发的核心知识：

- LLM 对自然语言需求的理解。
- Vision 模型对图片的结构化识别。
- 用户 Memory 的设计与更新。
- RAG 或数据库查询在 Agent 中的应用。
- Tool Calling 的真实业务场景。
- 多步骤 Workflow 的编排。
- 图片生成和虚拟试穿能力。
- 小程序、云函数、数据库、云存储的完整产品链路。

建议先把第一版做小、做完整、做稳定。只要完成“上传衣服 -> AI 识别 -> 查询衣柜 -> 生成搭配 -> 保存反馈”这个闭环，这个项目就已经是一个真正的 AI Agent 产品雏形。



整个项目的核心链路都涉及 AI Agent 知识，按概念分：

  ---
  Vision（多模态识别）
  
  上传衣服 → AI 识别 — clothes.js analyze

  用户拍一张衣服照片 → 豆包视觉模型看图 → 结构化输出
  JSON（分类、颜色、材质、风格、季节、场景）。图片不能直接用于数据库检索，所以 Vision 把像素转成可查询的结构化字段。

  // 直接调豆包视觉模型，输入图片+prompt
  input: [{ role: 'user', content: [
    { type: 'input_image', image_url },
    { type: 'input_text', text: prompt },
  ]}]

  ---
  Memory（长期记忆）
  
  三层记忆体系：

  ┌──────────┬─────────────────────────────────────────────────────────┬─────────────────┐
  │ 记忆类型 │                        数据来源                         │      存储       │
  ├──────────┼─────────────────────────────────────────────────────────┼─────────────────┤
  │ 用户画像 │ 用户主动填写（性别、身高、风格偏好）                    │ user_profile 表 │
  ├──────────┼─────────────────────────────────────────────────────────┼─────────────────┤
  │ 偏好记忆 │ 穿搭反馈自动压缩（收藏→偏好、不喜欢→黑名单、穿着→频次） │ ai_memory 表    │
  ├──────────┼─────────────────────────────────────────────────────────┼─────────────────┤
  │ 对话记忆 │ 聊天上下文摘要                                          │ ai_memory 表    │
  └──────────┴─────────────────────────────────────────────────────────┴─────────────────┘

  outfit.js feedback 里每次用户点"收藏/不喜欢/今天穿"都会调用 updatePreferenceMemory() 把反馈压缩成结构化偏好，写入
  ai_memory。

  ---
  Context（上下文拼装）
  
  生成穿搭 — outfit.js generate

  Agent 不能凭空推荐，每次调用豆包前先把四类数据拼成 Context：

  promptPayload = {
    outfit_request: { scene, weather, temperature },  // 用户当前需求
    user_profile: { gender, preferred_styles, ... },  // 长期画像
    preference_memory: { liked_colors, disliked_styles, ... }, // 反馈记忆
    wardrobe_items: [{ _id, name, color, category, ... }]       // 真实衣柜
  }

  ---
  Tool Calling（工具调用）
  
  穿搭 Agent 的工具抽象在 outfit.js searchCloset 里：

  - searchCloset() — 查衣柜：按场景、温度、偏好记忆给每件衣服打分排序，选 top 40 件
  - getProfile() — 读用户画像
  - getPreferenceMemory() — 读偏好记忆

  当前是代码按固定顺序调工具，还没到 LLM 自己决定调用哪个工具的阶段。

  ---
  Structured Output（结构化输出）
  
  所有豆包调用都要求输出严格 JSON：

  ┌──────────┬────────┬──────────────────────────────────────────────────────┐
  │   功能   │  模型  │                         输出                         │
  ├──────────┼────────┼──────────────────────────────────────────────────────┤
  │ 图片识别 │ Vision │ { category, type, color, style_tags, ... }           │
  ├──────────┼────────┼──────────────────────────────────────────────────────┤
  │ 穿搭生成 │ Text   │ { outfits: [{ title, clothes_ids, reason, score }] } │
  ├──────────┼────────┼──────────────────────────────────────────────────────┤
  │ 对话意图 │ Text   │ { type, intent, request, reply }                     │
  └──────────┴────────┴──────────────────────────────────────────────────────┘

  代码里 normalizeAiOutfits() 会校验 LLM 返回的 clothes_ids 是否都在真实衣柜中，防止 AI 编造衣服。

  ---
  Workflow（任务编排）
  
  穿搭生成完整流程 — outfit.js generate：

  用户请求 → 读衣柜 → 读画像 → 读记忆
    → searchCloset 打分筛选 40 件
    → 豆包生成候选搭配（JSON）
    → 校验 clothes_ids 是否真实存在
    → 写 outfit_records 落库
    → 写 ai_tasks 日志

  豆包调用失败自动重试一次 → 仍失败规则兜底，保证产品可用。

  ---
  多轮对话 Agent
  
  chat.js send — 真正的 LLM 意图识别：

  用户说 "明天海边怎么穿"
    → 豆包判断意图 → outfit_generate，置信度 0.85
    → 信息不够 → 追问 "大概什么天气？多少度？"
    → 用户补充 → 调 outfit.generate 生成搭配
    → 对话记忆写入 ai_memory

  ---
  可观测性
  
  ai_tasks 表 — 记录每次 AI 调用的完整生命周期：

  created → running（记 Prompt 和上下文摘要）
    → 模型返回（记原始输出 raw_text）
    → success（记候选摘要）
    或 → failed（记错误原因 + 兜底原因）

  不是黑盒，每次调 Prompt、模型返回了什么、为什么兜底都有迹可查。

  ---
  家居日常总结
  
  你打开衣柜 → 拍照 → AI 认出来"白色宽松 T 恤、棉质、夏季、休闲"→ 衣柜里有 30 件衣服了 → 对 AI 说"明天去海边，30 度" →
  AI 查你的衣柜、结合你之前收藏过的搭配、避开你不喜欢的荧光色 → 挑出白色 T 恤 + 卡其短裤 + 凉鞋 → 解释为什么这样搭 →
  你点"喜欢这套" → 系统记住你偏好白色+卡其色的海边搭配。下次类似场景，这套偏好自动影响推荐排序。
